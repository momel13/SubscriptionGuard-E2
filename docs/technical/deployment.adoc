== Umgebungsübersicht

Das System wird in mehreren Umgebungen betrieben, die unterschiedliche Zwecke haben. Jede Umgebung ist vollständig isoliert. Eine Änderung in einer Umgebung beeinflusst keine andere.

[cols="1,1,2,1,1", options="header"]
|===
| Umgebung | URL | Zweck | Branch | Deployment

| Lokal
| http://localhost:3000 (Frontend) +
  http://localhost:5000 (Backend)
| Entwicklung und manuelle Tests auf dem eigenen Rechner
| Beliebig
| Manuell (npm / Docker / Supabase CLI)

| CI
| —
| Automatische Qualitätsprüfung bei jedem Push
| Alle Branches
| Automatisch (GitHub Actions)

| Staging
| https://staging.subscriptionguard.app
| Integrationstest; Abnahme durch Product Owner vor Release
| `main`
| Automatisch nach Merge in `main`

| Produktion
| https://subscriptionguard.app
| Live-System für Endnutzer:innen
| `main` (getaggt)
| Manuell mit Freigabe
|===

NOTE: In der Hochschulumgebung entfällt oft eine separate Produktionsumgebung. In diesem Fall dient Staging gleichzeitig als Produktionsumgebung.

== Lokale Entwicklungsumgebung

Diese Anleitung richtet sich an neue Teammitglieder, die das System zum ersten Mal lokal zum Laufen bringen wollen. 

=== Voraussetzungen

[cols="1,1,2", options="header"]
|===
| Werkzeug | Version | Installationshinweis

| Node.js
| ≥ 20 LTS
| https://nodejs.org (Empfehlung: Installation via `nvm`)

| Docker
| ≥ 24.0
| https://docs.docker.com/get-docker/ (Wird für die lokale DB via Supabase CLI benötigt)

| Supabase CLI
| Aktuell
| https://supabase.com/docs/guides/cli/getting-started

| Git
| Aktuell
| https://git-scm.com
|===

=== System lokal starten

[source,bash]
----
# 1. Repository klonen
git clone [Repository-URL]
cd SubscriptionGuard

# 2. Umgebungsvariablen konfigurieren
# Für Backend und Frontend die .env-Dateien anlegen
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
# .env Dateien mit den auf Discord geteilten Werten füllen

# 3. Abhängigkeiten installieren
cd backend && npm install
cd ../frontend && npm install
cd ..

# 4. Lokale Supabase-Datenbank starten (optional, falls nicht die Cloud-DB genutzt wird)
npx supabase start

# 5. Frontend & Backend im Dev-Modus starten (zwei Terminal-Fenster)
# Terminal 1 (Backend):
cd backend && npm run dev
# Terminal 2 (Frontend):
cd frontend && npm run dev

# 6. Prüfen, ob alles läuft
# Frontend:  http://localhost:3000
# Backend:   http://localhost:5000/api/dashboard
----

=== System stoppen und aufräumen

[source,bash]
----
# Lokale Entwicklungsserver stoppen
Strg+C (bzw. Ctrl+C) in den jeweiligen Terminals

# Lokale Supabase-Container stoppen (falls gestartet)
npx supabase stop

# Lokale DB komplett zurücksetzen (löscht alle lokalen Daten!)
npx supabase stop --no-backup
----

=== Häufige Probleme beim lokalen Start

[cols="2,3", options="header"]
|===
| Problem | Lösung

| Port bereits belegt (`address already in use`)
| Prüfen, ob noch ein Node-Prozess läuft:
  `lsof -i :5000` (macOS/Linux) bzw. `netstat -ano` (Windows) und diesen beenden.

| Datenbank-Verbindung schlägt fehl
| Prüfen, ob in der `backend/.env` die `DATABASE_URL` korrekt eingetragen ist (Passwort vergessen?). Bei Nutzung des Transaction Poolers prüfen, ob Port 6543 nicht durch eine Firewall blockiert wird.

| Supabase Auth liefert 401 Unauthorized
| Prüfen, ob die `SUPABASE_URL` und der `SUPABASE_ANON_KEY` in der `.env` exakt mit dem Cloud-Projekt übereinstimmen.
|===


== Docker & Container (Produktion)

Dieser Abschnitt beschreibt, wie das System für Staging/Produktion containerisiert ist.

=== Container-Übersicht

[cols="1,1,2,1", options="header"]
|===
| Service | Image | Zweck | Port (intern → extern)

| frontend
| node:20-alpine (Build-Image)
| React/Vite-Anwendung — wird als statische Dateien gebaut und über nginx ausgeliefert.
| 80 → 3000

| backend
| node:20-alpine
| Express.js REST-API und Cron-Jobs (Deadline Check).
| 5000 → 5000

| db & auth
| Managed by Supabase
| PostgreSQL-Datenbank und Authentifizierungs-Dienste laufen als Managed Service in der Cloud (eu-central-1).
| 5432 / 6543 (Pooler)
|===

=== Umgebungsvariablen

Alle Konfiguration erfolgt über Umgebungsvariablen und *nicht* über feste Werte im Code. Eine vollständige Liste mit Beispielwerten befindet sich in `backend/.env.example`.

[cols="1,1,2,1", options="header"]
|===
| Variable | Beispielwert | Beschreibung | Pflicht

| `PORT`
| `5000`
| Der Port, auf dem der Express-Server läuft.
| Ja

| `DATABASE_URL`
| `postgresql://postgres.[ID]:[PASS]@aws-0-eu-central-1.pooler.supabase.com:6543/postgres`
| Verbindungs-URL zur Supabase-Datenbank (inkl. Passwort).
| Ja

| `SUPABASE_URL`
| `https://[ID].supabase.co`
| Die Basis-URL des Supabase-Projekts für das Auth-SDK.
| Ja

| `SUPABASE_ANON_KEY`
| `sb_publishable_...`
| Der öffentliche API-Schlüssel für Supabase.
| Ja
|===

IMPORTANT: Produktions-Secrets (Passwörter für die `DATABASE_URL`) werden *nie* im Repository gespeichert — auch nicht in `.env`-Dateien. Sie werden ausschließlich als CI/CD-Secrets in GitHub oder über einen Secret-Manager verwaltet.

== CI/CD-Pipeline

Die Pipeline automatisiert Qualitätsprüfung und Deployment. Sie stellt sicher, dass kein Code in `main` gelangt, der Tests bricht oder Qualitätsstandards verletzt.

=== Pipeline-Schritte im Detail

[cols="1,2,1,1", options="header"]
|===
| Schritt | Beschreibung | Schlägt fehl bei | Ausgeführt bei

| Linting
| Code-Stil (ESLint) und Typ-Prüfung (TypeScript)
| Stilfehler, TypeScript-Fehler oder Warnungen über Schwellwert
| Jedem Push

| Unit-Tests
| Vitest ausführen
| Fehlschlagende Tests
| Jedem Push

| Image-Build
| Docker-Images für Frontend und Backend bauen
| Build-Fehler
| Jedem Push auf `main` und PRs

| Staging-Deployment
| Neue Images auf Staging-Umgebung ausrollen
| Deployment-Fehler oder fehlschlagende Smoke Tests
| Merge in `main`

| Produktions-Deployment
| Neues Release auf Produktion ausrollen
| Deployment-Fehler oder fehlschlagende Smoke Tests
| Manuell nach Tag-Erstellung
|===

=== Pipeline-Konfiguration

Die vollständige Pipeline-Konfiguration befindet sich in:

[source]
----
.github/workflows/
├── ci.yml          ← Qualitätsprüfung (bei jedem Push)
└── deploy.yml      ← Deployment (Staging & Produktion)
----


== Deployment-Ablauf

=== Deployment auf Staging (automatisch)

Jeder Merge in `main` löst automatisch ein Deployment auf Staging aus. Kein manueller Eingriff erforderlich.

. Pipeline baut neue Docker Images für Node-Backend und Nginx-Frontend.
. Images werden in die Container-Registry gepusht.
. Staging-Umgebung zieht die neuen Images.
. Smoke Tests werden automatisch ausgeführt.
. Team wird bei Erfolg oder Fehler benachrichtigt.

=== Release und Deployment auf Produktion (manuell)

[source,bash]
----
# 1. Sicherstellen, dass main aktuell und stabil ist
git checkout main
git pull

# 2. Release-Tag erstellen (Semantic Versioning)
git tag v1.2.0
git push --tags

# 3. In GitHub Actions: Produktions-Deployment manuell freigeben
# → GitHub → Actions → deploy.yml → "Run workflow" → Version bestätigen
----

NOTE: Wir verwenden _Semantic Versioning_ mit dem Schema MAJOR.MINOR.PATCH: 
MAJOR bei inkompatiblen Änderungen,
MINOR bei neuen Features (abwärtskompatibel),
PATCH bei Bugfixes.

=== Smoke Tests nach Deployment

Nach jedem Deployment werden folgende Prüfungen ausgeführt:

[cols="2,2", options="header"]
|===
| Prüfung | Erwartetes Ergebnis

| `GET /api/health` (Backend)
| HTTP 200, JSON `{ "status": "UP" }`

| Startseite laden (Frontend)
| HTTP 200, Ladezeit < 3 s

| DB-Verbindung (Backend)
| `/api/health` prüft intern einen simplen `SELECT 1` gegen Supabase.

| Auth-Flow
| Login mit Test-Token erfolgreich, API liefert HTTP 200 statt 401.
|===

== Rollback

Ein Rollback ist notwendig, wenn ein Deployment kritische Fehler in der Produktionsumgebung verursacht. Schnelles Handeln minimiert die Auswirkungen.

=== Wann wird ein Rollback durchgeführt?
* Kritische API-Fehler (500) nach einem Deployment.
* Smoke Tests schlagen nach Deployment fehl.
* App-Abstürze oder fehlschlagende Datenbankverbindungen.

=== Rollback-Ablauf

. *Entscheidung treffen* — Tech Lead oder Product Owner entscheiden über Rollback.
. *Stakeholder informieren* — Team benachrichtigen.
. *Rollback ausführen* (eine von zwei Optionen):

[source,bash]
----
# Option A: Letztes stabiles Tag erneut deployen
# → GitHub → Actions → deploy.yml → Version des letzten stabilen Tags eingeben

# Option B: Manuell das vorherige Image aktivieren
docker compose pull backend:[vorherige-version] frontend:[vorherige-version]
docker compose up -d
----

[start=4]
. *Smoke Tests ausführen* — sicherstellen dass das System wieder stabil ist.
. *Ursache analysieren* — was hat das Problem verursacht?
. *Nachbereitung dokumentieren* — im Ticket oder als Kommentar im ADR.

== Monitoring & Logging

Dieser Abschnitt beschreibt, wie der Zustand des Systems beobachtet und wie Fehler diagnostiziert werden können.

=== Health Checks

[cols="1,2,1", options="header"]
|===
| Endpunkt | Beschreibung | Erwartet

| `GET /api/health`
| Gesamtstatus des Express-Servers inkl. Datenbankverbindung zu Supabase.
| HTTP 200, `{"status": "UP"}`
|===

=== Logs

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Log-Format
| Console-Logs im JSON-Format; enthält Zeitstempel, Level, Route, Message.

| Log-Zugriff (lokal)
| Direkt im Terminal des ausgeführten `npm run dev` Befehls.

| Log-Zugriff (Produktion)
| Über die Logs des jeweiligen Container-Hostings (z.B. `docker compose logs -f backend`).

| Was geloggt wird
| Server-Abstürze (ERROR), fehlschlagende JWT-Prüfungen (WARN), Backend-Starts (INFO).

| Was *nicht* geloggt wird
| Nutzerpasswörter (werden von Supabase gehandhabt), Tokens, sensible Finanzdaten oder CSV-Inhalte (DSGVO-Anforderung).
|===
