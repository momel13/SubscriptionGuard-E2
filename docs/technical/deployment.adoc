Dieses Dokument beschreibt die Schritte zur Installation und lokalen Ausführung des Prototyps für das Projekt SubscriptionGuard. Diese Anleitung dient als technische Evilenze für die lokale Lauffähigkeit unseres Walking Skeletons (Aufgabe 3.6).

_Dieses Dokument beschreibt, wie das System gebaut, ausgeliefert und betrieben wird: 
lokal, in der CI/CD-Pipeline und in den verschiedenen Umgebungen. Es richtet sich
primär an Entwickler:innen und deckt das ab, was nach dem Schreiben von Code passiert._

_Technische Entscheidungen rund um Containerisierung und CI/CD (das *Warum*) sind
als ADRs im link:architecture.adoc[Architekturdokument] (`architecture.adoc`) dokumentiert. Dieses Dokument beschreibt das *Wie* und *Was*._

== Voraussetzungen

Für das Ausführen des Prototyps müssen folgende Tools auf dem lokalen System installiert sein:
* **Node.js** (Empfohlen: Version 18 LTS oder neuer)
* **Webbrowser** (Chrome, Firefox oder Safari mit aktivierter JavaScript-Unterstützung)
* **Git** (Zum Klonen des aktuellen Repository-Standes)

== Lokale Ausführung (Schritt-für-Schritt)

Bitte diese Befehle nacheinander im Terminal ausführen:

=== 1. Repository klonen und verifizieren
Öffnen Sie Ihr Terminal und klonen Sie das Projekt-Repository:
[source,bash]
----
git clone <Hier steht der GitHub-Link zu eurem Projekt>
cd SubscriptionGuard-E2
----

=== 2. Abhängigkeiten installieren
Wir installieren die benötigten Bibliotheken (wie Chart.js für die Diagramme) direkt im Hauptverzeichnis:
[source,bash]
----
npm install
----

=== 3. Datenquelle (Data Source) verstehen
Unser System besitzt zwei Betriebsmodi für die Datenversorgung:
* **Mock-Datenmodus (Standard):** Nutzt das Objekt `MockDataSource` mit vordefinierten Testdaten (`MOCK_DASHBOARD`).
* **REST API-Modus (Zielbild):** Wechselt automatisch auf die echte API, wenn `window.SubGuardDataSource` vom Backend registriert ist:
[source,javascript]
----
window.SubGuardDataSource = { 
  name: 'REST API', 
  loadDashboard: async () => fetch('/api/dashboard').then(r => r.json()) 
};
----

=== 4. Prototyp starten
Starten Sie den lokalen Entwicklungsserver mit folgendem Befehl:
[source,bash]
----
npm run dev
----

== Verifikation und Funktionsprüfung (Testing)

Nach dem erfolgreichen Start können Sie das Walking Skeleton über die Browser-Konsole (F12) und die Benutzeroberfläche so überprüfen:

=== 1. Überprüfung des App-Zustands (App State)
Die Funktion `init()` lädt beim Start alle Daten. Stellen Sie sicher, dass das Objekt `appState` folgende Kernkomponenten erfolgreich gerendert hat:
* **Kosten-Karten (`renderDashboard`):** Überprüfung der monatlichen Kosten (berechnet über `INTERVAL_FACTOR` und `monthCost`).
* **Fristen-Liste:** Anzeige der kommenden Fristen (z. B. McFit Kündigung in 4 Tagen, berechnet über die Funktion `daysUntil`).
* **Budget-Komponente (`renderBudget`):** Anzeige, ob die Ausgaben im Rahmen des `budgetTarget` (Standard: 80 EUR) liegen.
* **Erinnerungen (`renderNotifications`):** Anzeige im Notification Center (z. B. "Monatsbudget zu 92 % aufgebraucht").

=== 2. Datenquellen-Label prüfen
Sehen Sie ganz unten auf dem Bildschirm nach. Das System gibt eine automatische Rückmeldung über die geladenen Daten:
* `Klickbarer Prototyp — Mock-Daten` (Standard-Lokalkonfiguration).
* `Klickbarer Prototyp — REST API` (Wenn die echte Backend-Verbindung aktiv ist).
