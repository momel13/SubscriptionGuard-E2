== Teststrategie

_Beschreibe in wenigen Sätzen den grundsätzlichen Ansatz zur Qualitätssicherung im Projekt.
Warum wurden diese Testarten gewählt? Welchen Stellenwert hat Testing im Team?_

Für den Walking Skeleton liegt unser Fokus vor allem darauf, zu prüfen, ob die einzelnen Teile unserer Architektur überhaupt
korrekt zusammenarbeiten. Dabei soll getestet werden, ob das React-Frontend Requests an das Node/Express-Backend senden kann
und ob das Backend anschließend erfolgreich Daten aus der Supabase-PostgreSQL-Datenbank abruft.

Es geht noch nicht um die vollständige Umsetzung aller Features oder komplexe Geschäftslogik. Stattdessen
steht der technische Durchstich der Datenpipeline im Vordergrund. Konkret wird überprüft, ob Daten korrekt vom Frontend über
das Backend zur Datenbank und wieder zurück übertragen und anschließend im UI angezeigt werden können.

== Testarten

=== Unit-Tests

Unit-Tests prüfen einzelne Klassen oder Funktionen isoliert voneinander.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Überprüfung einzelner Hilfsfunktionen und Daten-Mapping-Funktionen in Isolation

| Umfang
| Mapping von snake_case zu camelCase sowie einfache Backend-Hilfsfunktionen

| Werkzeug
| Vitest / Jest

| Mocking (Faken / Simulieren)
| Supabase-Responses können für isolierte Tests gemockt werden

| Abdeckungsziel
| Kein fester Zielwert im Walking Skeleton; Fokus liegt auf Integrationsfähigkeit

| Ausführung
| Lokal während der Entwicklung
|===

=== Integrationstests

Integrationstests prüfen das Zusammenspiel mehrerer Komponenten, z. B. Service und Datenbank.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Sicherstellung der fehlerfreien Kommunikation zwischen Frontend, Backend und Supabase-Daten

| Umfang
| GET /api/dashboard, Datenbankzugriff, Daten-Mapping, API-Responses

| Werkzeug
| Express, fetch API, Browser DevTools, Postman

| Testdaten
| Seed-Daten in der Supabase-Cloud-Datenbank

| Ausführung
| Manuell während der Entwicklung und vor jedem Meilenstein-Review
|===

=== Optional: End-to-End-Tests (E2E)

E2E-Tests simulieren echte Nutzerinteraktionen durch die gesamte Anwendung.

//E2E-Tests sind optional und sollten erst betrachtet werden, wenn alle anderen Testarten ausreichend berücksichtigt wurden.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Überprüfung des vollständigen technischen Durchstichs aus Nutzersicht

| Umfang
| Dashboard laden und Daten aus der Datenbank im UI anzeigen

| Werkzeug
| Manuelle Browser-Tests (Playwright/Cypress optional später)

| Ausführung
| Manuell im Browser
|===

=== Manuelle Tests

Hier werden alle Tests aufgeführt, die nicht automatisiert werden können.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Überprüfung der technischen Integration sowie der sichtbaren UI-Funktionalität

| Umfang
| Dashboard-Aufruf, API-Kommunikation, Fehleranzeige

| Vorgehen
| Frontend wird lokal gestartet und sendet Requests an das lokale Express-Backend.
Das Backend ruft reale Seed-Daten aus Supabase ab.
Die Antworten werden im Browser und in den DevTools überprüft.


| Dokumentation
| Testergebnisse werden als Kommentar oder Anhang im GitHub-Issue dokumentiert
|===

== Testabdeckung

_Definiert die angestrebten Mindestwerte für die Testabdeckung._

[cols="1,1,2", options="header"]
|===
| Schicht | Zielwert | Bemerkung

| Service-Schicht
| [z. B. ≥ 80 %]
| Geschäftslogik hat höchste Priorität

| Persistenz-Schicht
| [z. B. ≥ 60 %]
| Grundlegende CRUD-Operationen abgedeckt

| Controller / API
| [z. B. ≥ 70 %]
| Wichtigste Endpunkte per Integrationstest abgedeckt

| Frontend-Komponenten
| [z. B. ≥ 50 %]
| Fokus auf wiederverwendbare Kernkomponenten
|===

NOTE: Abdeckung ist kein Selbstzweck. 80 % sinnlose Tests sind schlechter als 60 % gut durchdachte Tests. Qualität der Tests ist wichtiger als der Prozentwert.

== Integration in den Entwicklungsprozess

=== Ausführung der Tests
==== Lokale Entwicklung
[source,bash]
----
# Alle Unit-Tests ausführen
[z. B.  pytest  |  npm test]

# Testabdeckung prüfen
[z. B.  pytest --cov]
----

==== CI-Pipeline

Tests werden automatisch bei jedem Push im Repository ausgeführt. Je nach Testart können unterschiedliche Trigger und Umgebungen sinnvoll sein. Die Konfiguration der CI-Pipeline sollte sicherstellen, dass alle Tests zuverlässig und schnell ausgeführt werden.

=== Definition of Done

//Bitte anpassen und nur das aufnehmen, was tatsächlich auch durchgeführt wird.
Folgende Testkriterien sind Teil unserer Definition of Done:

* [ ] Alle bestehenden Tests sind grün
* [ ] Neue Funktionalität ist durch Unit-Tests abgedeckt
* [ ] Die Mindest-Testabdeckung wird nicht unterschritten
* [ ] Manuelle Tests für neue Features wurden durchgeführt
* [ ] Keine bekannten kritischen Fehler sind offen
