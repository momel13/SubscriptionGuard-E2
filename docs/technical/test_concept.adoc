== Teststrategie

Für den Walking Skeleton liegt unser Fokus hauptsächlich darauf, frühzeitig zu überprüfen,
ob die grundlegende Architektur des Systems korrekt funktioniert und die einzelnen Schichten
miteinander kommunizieren können.

Dabei wird getestet, ob:

* das React-Frontend erfolgreich Requests senden kann,
* das Node/Express-Backend diese Requests korrekt verarbeitet,
* die Verbindung zur Supabase PostgreSQL-Datenbank funktioniert,
* und die Daten anschließend korrekt im Frontend dargestellt werden.

Im Mittelpunkt steht dabei nicht die vollständige Geschäftslogik oder die finale Umsetzung
aller Features, sondern der technische Durchstich der Datenpipeline.

Zusätzlich wird überprüft, ob Datenbankfelder korrekt von `snake_case`
(z. B. `category_id`) in das vom Frontend erwartete `camelCase`
(z. B. `categoryId`) umgewandelt werden.

Die Tests werden aktuell überwiegend manuell durchgeführt, da sich das Projekt noch
in einer frühen Entwicklungsphase befindet und zunächst die technische Integrationsfähigkeit
der Architektur nachgewiesen werden soll.

== Testarten

=== Unit-Tests

Unit-Tests prüfen einzelne Funktionen isoliert voneinander.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Überprüfung einzelner Hilfsfunktionen und Daten-Mapping-Funktionen

| Umfang
| Mapping von `snake_case` auf `camelCase`, Formatierungsfunktionen und einfache Backend-Hilfslogik

| Werkzeug
| Vitest / Jest (geplant)

| Mocking (Faken / Simulieren)
| Supabase-Responses können für isolierte Tests simuliert werden

| Abdeckungsziel
| Kein fester Zielwert im Walking Skeleton; Fokus liegt zunächst auf der erfolgreichen Systemintegration

| Ausführung
| Lokal während der Entwicklung
|===

=== Integrationstests

Integrationstests prüfen das Zusammenspiel mehrerer Komponenten.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Sicherstellung der fehlerfreien Kommunikation zwischen Frontend, Backend und Supabase-Datenbank

| Umfang
| `GET /api/dashboard`, Datenbankzugriff, Daten-Mapping und API-Responses

| Werkzeug
| Express, fetch API, Browser DevTools, Postman

| Testdaten
| Seed-Daten aus der Supabase-Cloud-Datenbank (`categories` Tabelle)

| Ausführung
| Manuell während der Entwicklung und vor jedem Meilenstein-Review
|===

=== Optional: End-to-End-Tests (E2E)

E2E-Tests simulieren echte Nutzerinteraktionen durch die gesamte Anwendung.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Überprüfung des vollständigen technischen Durchstichs aus Nutzersicht

| Umfang
| Dashboard laden und Daten aus der Datenbank im Frontend anzeigen

| Werkzeug
| Manuelle Browser-Tests (Playwright oder Cypress optional später)

| Ausführung
| Manuell im Browser
|===

=== Manuelle Tests

Ein Großteil der aktuellen Tests wird manuell durchgeführt, um die technische Integration
des Walking Skeletons schrittweise zu überprüfen.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Überprüfung der technischen Integration sowie der sichtbaren UI-Funktionalität

| Umfang
| Dashboard-Aufruf, API-Kommunikation, CORS-Verhalten, Datenanzeige und Fehlerfälle

| Vorgehen
| Das Frontend wird lokal über Live Server gestartet und sendet Requests an das lokale Express-Backend.
Das Backend ruft reale Seed-Daten aus Supabase ab und liefert diese als JSON-Response zurück.
Die Ergebnisse werden lokal im Browser, über die DevTools,
über Thunder Client in VS Code sowie über Postman überprüft.

| Dokumentation
| Testergebnisse und Fehler werden im GitHub-Issue dokumentiert
|===

== Durchgeführte Walking-Skeleton-Tests

=== Test 1: Backend-Endpunkt erreichbar

Ziel dieses Tests war die Überprüfung, ob der lokale Express-Server korrekt gestartet werden kann und der Dashboard-Endpunkt erreichbar ist.

Dabei wurde getestet, ob der Endpunkt `/api/dashboard` erfolgreich eine gültige JSON-Response zurückliefert.

Ergebnis:

* Der Express-Server konnte fehlerfrei gestartet werden
* Der Dashboard-Endpunkt war lokal über Thunder Client und Postman erreichbar
* Die API lieferte gültige Dashboard-Daten zurück

Der Test wurde erfolgreich durchgeführt.

---

=== Test 2: Verbindung zur Supabase-Datenbank

Im nächsten Schritt wurde überprüft, ob das Backend erfolgreich Daten aus der Supabase-Cloud-Datenbank abrufen kann.

Für den Walking Skeleton wurden zunächst die Seed-Daten der Tabelle `categories` verwendet.

Ergebnis:

* Die Verbindung zur Datenbank funktionierte fehlerfrei
* Die Seed-Daten konnten erfolgreich geladen werden
* Die Daten wurden korrekt an das Backend zurückgegeben

---

=== Test 3: Daten-Mapping zwischen Datenbank und Frontend

Da die Datenbank SQL-Feldnamen im `snake_case`-Format verwendet, das Frontend jedoch `camelCase` erwartet, wurde zusätzlich das Daten-Mapping getestet.

Beispiele:

* `category_id` → `categoryId`
* `start_date` → `startDate`
* `is_paused` → `isPaused`

Das Mapping wurde über die Datei `dashboardMapper.ts` umgesetzt.

Ergebnis:

* Die Daten wurden korrekt umgewandelt
* Das Frontend konnte die Daten fehlerfrei verarbeiten

---

=== Test 4: Frontend-Integration

Das Frontend wurde so angepasst, dass keine lokalen Mock-Daten mehr verwendet werden.

Stattdessen lädt das Dashboard seine Daten nun direkt über das lokale Express-Backend.

Dabei wurde geprüft, ob:

* Requests erfolgreich vom Frontend gesendet werden
* das Backend korrekt antwortet
* die Daten anschließend im UI dargestellt werden

Ergebnis:

* Das Frontend konnte erfolgreich mit dem Backend kommunizieren
* Die Kategorien wurden korrekt im Dashboard angezeigt
* Es traten keine CORS- oder Netzwerkfehler auf

Damit konnte der technische Durchstich zwischen Frontend, Backend und Datenbank erfolgreich nachgewiesen werden.

---

=== Test 5: Port-Konflikt während der Entwicklung

Während der lokalen Entwicklung trat ein Konflikt mit Port `5000` auf, da dieser bereits von einem anderen Prozess verwendet wurde.

Zur Lösung des Problems wurde das Backend temporär auf Port `5001` umgestellt.

Das Frontend wurde anschließend entsprechend angepasst.

Ergebnis:

* Backend und Frontend konnten parallel lokal ausgeführt werden
* Die API-Kommunikation funktionierte anschließend fehlerfrei

== Testabdeckung

Da sich das Projekt aktuell noch im Walking-Skeleton-Stadium befindet, liegt der Schwerpunkt zunächst auf der erfolgreichen technischen Integration und weniger auf einer hohen automatisierten Testabdeckung.

[cols="1,1,2", options="header"]
|===
| Schicht | Zielwert | Bemerkung

| Backend API
| ≥ 60 %
| Fokus auf zentrale API-Endpunkte

| Daten-Mapping
| ≥ 70 %
| Kritisch für die Kommunikation zwischen Backend und Frontend

| Frontend-Komponenten
| ≥ 40 %
| Fokus auf Dashboard-Darstellung und Datenanzeige

| Datenbankintegration
| Manuelle Tests
| Datenfluss wurde praktisch überprüft
|===

NOTE: Die Qualität und Aussagekraft der Tests ist wichtiger als eine möglichst hohe prozentuale Testabdeckung.

== Integration in den Entwicklungsprozess

=== Ausführung der Tests

==== Lokale Entwicklung

Für die lokale Entwicklung wird das Backend über `npm run dev` gestartet.
Das Frontend wird anschließend lokal über den VS-Code-Live-Server ausgeführt.

=== Definition of Done

Folgende Kriterien gelten für den Walking Skeleton als erfüllt:

* [x] Frontend sendet Requests an das lokale Backend
* [x] Backend ruft Daten aus Supabase ab
* [x] Daten werden korrekt gemappt
* [x] Dashboard-Endpunkt liefert gültige Responses
* [x] Frontend rendert Daten erfolgreich
* [x] Keine kritischen Verbindungs- oder CORS-Fehler vorhanden

== Fehlerbehandlung & Bugtracking

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Wo werden Bugs erfasst?
| Als GitHub-Issues im Projekt-Repository

| Priorisierung
| Kritische API- oder Backend-Fehler werden direkt behoben

| Reproduzierbarkeit
| Fehler werden inklusive Beschreibung, Konsolen-Logs und Reproduktionsschritten dokumentiert.
Während des Walking Skeletons traten beispielsweise Probleme mit der Supabase-Verbindung und der lokalen Port-Konfiguration auf.
Die Ursachen konnten durch Überprüfung der `.env`-Variablen, der Serverstruktur sowie der lokalen Entwicklungsumgebung identifiziert und behoben werden.
|===
