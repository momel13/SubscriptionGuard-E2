=== ADR-001: Eine gemeinsame Sprache (TypeScript) für Frontend und Backend

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| {localdatetime}

| *Kontext*
| Da die Logik sowohl im Client (UI-Zustand, Formulare) als auch auf dem Server (Validierung, API, Cron-Jobs) läuft, besteht das Risiko von doppelter Code-Pflege und API-Vertragsbrüchen (API Drift).

| *Entscheidung*
| Wir verwenden TypeScript sowohl für das React-Frontend als auch für das Node.js/Express-Backend (als Monorepo). Die Typdefinitionen (`shared/types.ts`) werden von beiden Seiten importiert.

| *Alternativen*
| Java oder Python für das Backend. Wurde verworfen, da dies einen ständigen Context-Switch der Syntax erfordert und API-Schnittstellen (z.B. via Swagger/OpenAPI) aufwendiger synchronisiert werden müssen.

| *Konsequenzen*
| Frontend-Builds schlagen fehl, sobald das Backend ein Feld umbenennt, was Bugs vor dem Deployment verhindert. Geteilte Funktionen (wie `getCostPerMonth`) müssen nur einmal geschrieben und getestet werden.
|===


=== ADR-002: Supabase für Hosting und Authentifizierung statt Eigenentwicklung

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| {localdatetime}

| *Kontext*
| Die Implementierung von sicherer Authentifizierung (JWT, Bcrypt, Token-Refresh) sowie der Aufbau und das Hosting einer eigenen Datenbank verschlingen viel Zeit in studentischen Software-Engineering-Projekten.

| *Entscheidung*
| Wir lagern die Authentifizierung und das Datenbank-Hosting an Supabase (PostgreSQL-basiert) aus, behalten aber ein eigenes Express-Backend für komplexe Logik (CSV-Parsing, Cron-Jobs).

| *Alternativen*
| Lokale PostgreSQL via Docker + eigenes Auth-System via Passport.js. Verworfen, da zu fehleranfällig und aufwendig für das enge Zeitbudget des Projekts.

| *Konsequenzen*
| Beschleunigt den Weg zum MVP drastisch. Es entsteht ein Vendor Lock-in bei Supabase, der aber durch die Standard-PostgreSQL-Basis abgemildert wird.
|===



=== Technische Risiken

[cols="2,1,2,2", options="header"]
|===
| Risiko | Auswirkung | Wahrscheinlichkeit | Maßnahme

| SQL-Injection durch unsichere Queries
| Hoch
| Mittel
| IMMER Prepared Statements (`$1, $2...`) verwenden. Wird im Code-Review strikt geprüft.

| DSGVO-Verletzung bei Supabase-Hosting (Default: USA)
| Hoch
| Niedrig
| Bei Projektanlage ausdrücklich EU-Region (`eu-central-1`) wählen.

| Asynchrone Fehler im Backend legen Server lahm
| Hoch
| Mittel
| Globale Error-Middleware in Express + `express-async-errors` implementieren.

| Chart.js Bundle-Größe bläht Ladezeiten auf
| Mittel
| Mittel
| Nur benötigte Komponenten registrieren (z.B. `Chart.register(DoughnutController, ArcElement)`) statt kompletter Bibliothek.

| SQL-Dialekt-Differenzen zwischen SQLite (Dev) und Postgres (Prod)
| Mittel
| Mittel
| SQL-Features auf den gemeinsamen Nenner reduzieren oder für komplexere Queries Query-Builder nutzen.
|===

=== Technische Schulden

[cols="2,2,1", options="header"]
|===
| Beschreibung | Begründung für Kompromiss | Backlog-Eintrag

| Keine Echtzeit-Updates im Frontend (Polling statt WebSockets)
| Für den MVP und die reinen Erinnerungsfunktionen reicht asynchrone REST-Kommunikation völlig aus. | -

| Fehlende Frontend-Validierung schützt nicht vor mutwillig falscher API-Nutzung
| DevTools lassen Umgehung zu; Server-Side-Validation (Backend) hat daher absolute Priorität und reicht als primärer Schutz. | -
