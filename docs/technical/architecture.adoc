== 3.3 Architekturtreiber ableiten

=== Ziel und Quellen

Dieses Dokument beschreibt die Architektur von SubscriptionGuard als Gesamtsystem.
Es verbindet
die kompakten Gesamtarchitektur-Inhalte aus `architecture (1).adoc` mit den detaillierten
Frontend-Treibern aus der vorherigen Fassung von `architecture.adoc`.
Einbezogene fachliche und technische Quellen:

* `Hauptfunktionen-1-3.pdf`: Funktionskatalog F1-F8, Komponentenarchitektur, Klassendiagramm,
  Use Cases UC1-UC5, PAP 1-5, Chancen, Risiken, Praesentationsstruktur und Glossar.
* `SubscriptionGuard3.2-3.pdf`: Web-Stack-Mapping, Domaenenglossar, REST-API-Uebersicht,
  SQL-Schema, Shared TypeScript-Types, Code-Beispiele fuer PAP 1-5, Stack-Vorteile,
  technische Risiken und naechste Schritte.
* `architecture (1).adoc`: Systemkontext, Gesamt-Technologie-Stack, ADRs zu TypeScript und
  Supabase, technische Risiken und technische Schulden.
* vorherige `architecture.adoc`: detaillierte Frontend-Treiber, Frontend-Systemgrenze,
  Feature-Architektur, UI-Risiken und Frontend-ADRs.

=== Architektur-Anforderungen aus dem Produktkonzept

Die folgende Tabelle fasst die wichtigsten architekturwirksamen Anforderungen aus dem
Produktkonzept zusammen und verweist auf die ADR, in der die jeweilige Entscheidung
ausfuehrlich dokumentiert ist.

[cols="3,6,2",options="header"]
|===
|Anforderung (aus Produktkonzept) |Technische Konsequenz |Entscheidung

|*Datenverschluesselung sensibler Finanzdaten* +
_(Datensicherheit)_
|Da die Daten nicht mehr lokal auf dem Endgerät liegen, sondern zentral gespeichert werden, erfordert dies eine sichere Transportverschluesselung (HTTPS/TLS) und eine strikte Mandantentrennung in der Datenbank ueber Row Level Security (RLS) in Supabase.
|<<adr-002,ADR-002>>

|*Massen-Datenverarbeitung beim CSV-Import* +
_(Verzicht auf PSD2)_
|Das Parsen grosser Kontoauszuege und die Mustererkennung von Abos ist rechenintensiv.
Damit
die App beim Import nicht "einfriert", muss dieser Prozess asynchron ablaufen (z.B.
Auslagerung in Web Worker im Frontend oder ein lokales Node.js-Backend).
|<<adr-005,ADR-005>>

|*Dynamische Erweiterbarkeit* +
_(Wartbarkeit)_
|Um neue Kategorien in unter 30 Minuten hinzuzufuegen, darf die Architektur diese nicht "hart"
im Code (Hardcoding) verdrahten.
Sie erzwingt ein datenbankgetriebenes Modell (Kategorien als
DB-Entitaeten statt als statische Enums im Frontend).
|—

|*Keine automatische Kuendigung* +
_(Rechtliche Einschraenkung)_
|Das System darf rechtlich keine Vertraege kuendigen.
Architektonische Konsequenz: Das System
ist nach aussen hin geschlossen (abgesehen von Updates/Backups).
Es muessen keine komplexen
Outbound-Schnittstellen zu Drittanbietern (Netflix, Fitnessstudios etc.) entwickelt oder
gewartet werden.
|—

|*Cross-Platform-Verfuegbarkeit* +
_(Portabilitaet)_
|Die App soll auf mehreren Plattformen (Web, Mobile) funktionieren.
Dies erzwingt die Wahl
eines Cross-Platform-Stacks (wie React/Vite als PWA oder React Native) anstelle von nativer
iOS/Android-Entwicklung, um die Code-Basis (Single Codebase) teilbar zu halten.
|<<adr-001,ADR-001>>
|===

== 3.5 Architekturentscheidungen dokumentieren

[[adr-001]]
=== ADR-001: Eine gemeinsame Sprache mit TypeScript fuer Frontend und Backend

*Status:* akzeptiert

*Kontext:* Frontend und Backend verwenden dieselben Domaenenbegriffe.
Ohne gemeinsame Typen
entsteht API-Drift, z.B. bei Feldern wie `cancelDeadline`, `usageRating` oder
`savingsPotential`.

*Entscheidung:* Frontend und Backend werden in TypeScript umgesetzt.
Zentrale
Typdefinitionen und reine Domaenenfunktionen liegen in `shared/types.ts`.

*Alternativen:* Java, Python oder andere Backend-Sprachen. Verworfen, weil dadurch mehr
Synchronisationsaufwand fuer API-Vertraege entsteht.
*Konsequenzen:* Der Build erkennt Feldumbenennungen frueh. Hilfsfunktionen wie
`getCostPerMonth` koennen gemeinsam getestet und wiederverwendet werden.

[[adr-002]]
=== ADR-002: Supabase fuer PostgreSQL-Hosting und Authentifizierung

*Status:* akzeptiert

*Kontext:* Eigene Authentifizierung mit JWT, Password Reset, Token Refresh und sicherem
DB-Hosting ist fehleranfaellig und fuer ein studentisches Projekt zeitintensiv.
*Entscheidung:* Authentifizierung und PostgreSQL-Hosting werden an Supabase ausgelagert. Dies gilt sowohl fuer die Produktion (Cloud-Instanz) als auch fuer die lokale Entwicklung via Supabase CLI (lokaler Docker-Container).
Ein eigenes Express-Backend bleibt fuer komplexe Logik wie CSV-Parsing, Analyse und Cron-Jobs erhalten.

*Alternativen:* Eigene PostgreSQL-Instanz plus Passport/Auth-Library.
Verworfen fuer den MVP,
weil Setup- und Sicherheitsaufwand hoeher sind.

*Konsequenzen:* Der MVP kommt schneller voran.
Es entsteht eine gewisse Supabase-Bindung, die
durch PostgreSQL als Standardbasis abgemildert wird. EU-Region ist verpflichtend zu waehlen.

[[adr-003]]
=== ADR-003: REST/JSON als primaere Schnittstelle

*Status:* akzeptiert

*Kontext:* Die Vorarbeit definiert REST-Endpunkte fuer alle Kernablaeufe.
Das Team braucht eine
einfache, gut verstaendliche Schnittstelle.

*Entscheidung:* Das Frontend kommuniziert mit dem Backend ueber REST/JSON. CSV-Uploads laufen
ueber `FormData`.
Backend und Datenbank werden nicht direkt aus dem Frontend angesprochen,
ausser Auth-Flows ueber Supabase Auth.

*Konsequenzen:* Die Architektur bleibt einfach.
Realtime-Funktionen werden erst bei Bedarf
ergaenzt.

[[adr-004]]
=== ADR-004: Chart.js fuer Analysevisualisierungen

*Status:* akzeptiert

*Kontext:* PAP 3 fordert ein Analyse-Dashboard mit Diagrammen.
Die benoetigten Diagrammtypen
sind Standardfaelle.

*Entscheidung:* Kategorieaufschluesselung, Kostenentwicklung und Prognosen werden mit Chart.js
visualisiert.

*Konsequenzen:* Nur benoetigte Komponenten werden registriert.
Bei vielen Kategorien werden
Top-5 plus "Sonstige" und Tabellenansichten genutzt.

[[adr-005]]
=== ADR-005: Backend fuer rechenintensive und zeitgesteuerte Fachlogik

*Status:* akzeptiert

*Kontext:* CSV-Erkennung, Kostenaggregation und taegliche Fristenpruefung duerfen das Frontend
nicht blockieren und brauchen Zugriff auf persistente Daten.
*Entscheidung:* CSV-Parsing, Mustererkennung, Analyseaggregation und Deadline-Check laufen im
Backend bzw. in SQL.
Das Frontend stellt nur UI, Upload, Review und Anzeige bereit.

*Konsequenzen:* Der Browser bleibt stabil.
Backend und Datenbank tragen mehr fachliche
Verantwortung, muessen also gut getestet werden.

[[adr-006]]
=== ADR-006: Feature-orientierte Frontend-Struktur mit Mantine

*Status:* akzeptiert

*Kontext:* F1-F8 bilden natuerliche Produktbereiche. Die UI braucht viele Standard-Controls.
*Entscheidung:* Das Frontend wird nach Features structured (`subscriptions`, `analysis`,
`budget`, `import`, `notifications`, `settings`, `auth`) und nutzt Mantine fuer robuste
UI-Bausteine.
*Konsequenzen:* Fachliche Aenderungen bleiben lokal. Standard-Controls muessen nicht selbst
gebaut werden.

[[adr-007]]
=== ADR-007: Notification Center plus optionaler Browser Push

*Status:* akzeptiert

*Kontext:* Push-Berechtigungen koennen abgelehnt werden, Erinnerungen muessen aber trotzdem
sichtbar bleiben.
*Entscheidung:* Das Frontend bietet immer ein In-App Notification Center. Browser Notifications
werden optional per Service Worker aktiviert.
*Konsequenzen:* Die App bleibt nutzbar, auch wenn Push nicht erlaubt ist.

[[adr-008]]
=== ADR-008: Datenschutzfreundliches Frontend

*Status:* akzeptiert

*Kontext:* Finanzdaten und Kontoauszuege sind sensibel.
*Entscheidung:* Das Frontend verzichtet auf Drittanbieter-Tracking, speichert keine CSV-Rohdaten
dauerhaft und haelt fachliche Finanzdaten nur als kurzlebigen UI-/Server-State.
*Konsequenzen:* Datenschutzrisiko und Synchronisationskomplexitaet sinken. Offline-Faehigkeit
bleibt im Web-Frontend bewusst begrenzt.
