== Ziel des Dokuments

Dieses Dokument beschreibt das Mapping zwischen den Daten aus der Supabase/PostgreSQL-Datenbank und dem vom Frontend erwarteten API-Format für das Walking Skeleton in Aufgabe 3.6.

Die Datenbank verwendet `snake_case`, während das Frontend laut `frontend-backend-contract.md`, `design.adoc` und `walking-skeleton-guide.adoc` Daten im `camelCase`-Format erwartet.

Das Mapping ist deshalb wichtig, damit das Frontend später nicht direkt von Datenbankspalten abhängig ist.

== Grundprinzip

Die Daten werden im Backend aus Supabase/PostgreSQL gelesen und dort in das erwartete Frontend-Format umgewandelt.

Dabei gilt:

* SQL-Tabellen und Spalten bleiben in `snake_case`.
* API-Responses verwenden `camelCase`.
* Das Frontend arbeitet nur mit fachlichen API-Daten.
* Supabase-Tabellen sollen nicht direkt vom Frontend für fachliche Daten gelesen werden.
* Secrets oder Service-Role-Keys dürfen niemals im Frontend verwendet werden.
* Geschützte Backend-Routen erhalten den Supabase Access Token über den
  HTTP-Header `Authorization: Bearer <access_token>`.
* Das Backend verwendet für echte Supabase-Requests einen request-spezifischen
  Supabase-Client, damit RLS mit dem aktuellen Nutzerkontext greift.

== Erwartetes Dashboard-Payload

Das Frontend erwartet für das Dashboard ungefähr folgende Struktur:

[source,ts]
----
type DashboardPayload = {
  categories: Category[];
  subscriptions: Subscription[];
  notifications: Notification[];
  importCandidates?: ImportCandidate[];
  budgetTarget: number;
};
----

== Mapping: Kategorien

Die Tabelle `categories` enthält bereits Seed-Daten und wird für die Kategorieauswahl und die Darstellung im Dashboard genutzt.

[cols="1,1,2", options="header"]
|===
| Datenbankfeld | API-Feld | Bemerkung

| `id`
| `id`
| Eindeutige ID der Kategorie.

| `name`
| `name`
| Name der Kategorie, z. B. Streaming, Musik oder Software.

| `icon`
| `icon`
| Icon für die Darstellung im Frontend.

| `color`
| `color`
| Farbe für Diagramme oder Kategorieanzeige.
|===

Beispiel:

[source,json]
----
{
  "id": 1,
  "name": "Streaming",
  "icon": "🎬",
  "color": "#a855f7"
}
----

== Mapping: Abonnements

Die Tabelle `subscriptions` enthält die wichtigsten fachlichen Daten für Abos. Hier ist das Mapping besonders wichtig, weil mehrere Datenbankspalten in `snake_case` vorliegen.

[cols="1,1,2", options="header"]
|===
| Datenbankfeld | API-Feld | Bemerkung

| `id`
| `id`
| Eindeutige ID des Abos.

| `user_id`
| `userId`
| Zuordnung zum Nutzer als `UUID`-String (Referenz auf `auth.users`). Für das Dashboard muss nach dem aktuellen Nutzer gefiltert werden.

| `category_id`
| `categoryId`
| Zuordnung zur Kategorie.

| `name`
| `name`
| Name des Abos.

| `provider`
| `provider`
| Anbieter, z. B. Netflix oder Spotify.

| `cost`
| `cost`
| Kosten des Abos. Sollte als Zahl zurückgegeben werden.

| `currency`
| `currency`
| Währung, z. B. `EUR`.

| `interval`
| `interval`
| Zahlungsintervall. Das Frontend erwartet z. B. `WEEKLY`, `MONTHLY`, `QUARTERLY`, `YEARLY`.

| `start_date`
| `startDate`
| Startdatum im Format `YYYY-MM-DD`.

| `cancel_deadline`
| `cancelDeadline`
| Kündigungsfrist. Kann auch `null` sein.

| `contract_end`
| `contractEnd`
| Vertragsende. Kann auch `null` sein.

| `auto_renewal`
| `autoRenewal`
| Gibt an, ob sich das Abo automatisch verlängert.

| `usage_rating`
| `usageRating`
| Nutzungsbewertung, z. B. `OFTEN`, `RARELY`, `NEVER`, `NOT_RATED`.

| `is_paused`
| `isPaused`
| Gibt an, ob ein Abo pausiert ist.

=== Request-Mapping: `POST /api/subscriptions`

Der aktuelle Prototyp verwendet diesen Endpoint, um ein neues Abo aus dem
Frontend-Formular heraus anzulegen. Das Frontend sendet die fachlichen Felder im
JSON-Body und den Supabase Access Token im Authorization-Header.

[cols="1,1,2", options="header"]
|===
| Request-Feld | Datenbankfeld | Bemerkung

| `categoryId`
| `category_id`
| Pflichtfeld. Muss auf eine vorhandene Kategorie verweisen.

| `name`
| `name`
| Pflichtfeld. Name des Abos, z. B. "Gym" oder "Netflix".

| `provider`
| `provider`
| Optionaler Anbietername.

| `cost`
| `cost`
| Pflichtfeld. Wird serverseitig als Zahl validiert.

| `currency`
| `currency`
| Standard im Prototyp: `EUR`.

| `interval`
| `interval`
| Erwartet `WEEKLY`, `MONTHLY`, `QUARTERLY` oder `YEARLY`. Aus Kompatibilitätsgründen akzeptiert das Backend auch `payment_interval` als Fallback.

| `startDate`
| `start_date`
| Optionales Datum im Format `YYYY-MM-DD`.

| `cancelDeadline`
| `cancel_deadline`
| Optionales Datum im Format `YYYY-MM-DD`.

| `contractEnd`
| `contract_end`
| Optionales Datum im Format `YYYY-MM-DD`.

| `autoRenewal`
| `auto_renewal`
| Boolescher Wert für automatische Vertragsverlängerung.

| `usageRating`
| `usage_rating`
| Nutzungsbewertung, z. B. `OFTEN`, `RARELY`, `NEVER`, `NOT_RATED`.
|===

Das Feld `user_id` wird nicht vom Frontend gesetzt. Es wird im Backend aus dem
geprüften Auth-Kontext des Bearer Tokens bestimmt. Dadurch kann Supabase RLS
sicherstellen, dass Nutzer nur eigene Abos schreiben oder lesen.

Erfolgreiche Antwort:

[source,json]
----
{
  "message": "Abo erfolgreich gespeichert.",
  "subscription": {
    "id": 13,
    "userId": "6c8aee4c-c003-4912-a1f7-1cc450...",
    "categoryId": 4,
    "name": "Gym",
    "provider": "FitX",
    "cost": 49.99,
    "currency": "EUR",
    "interval": "MONTHLY",
    "startDate": "2026-05-17",
    "cancelDeadline": "2027-06-15",
    "contractEnd": "2028-07-15",
    "autoRenewal": true,
    "usageRating": "OFTEN",
    "isPaused": false
  }
}
----

Fehlerfälle:

[cols="1,3", options="header"]
|===
| Status | Bedeutung

| `400`
| Request-Daten sind unvollständig oder fachlich ungültig.

| `401`
| Bearer Token fehlt oder ist ungültig.

| `500`
| Speichern in Supabase oder Erzeugen zugehöriger Notifications ist fehlgeschlagen.
|===

Wenn der lokale Demo-Login nicht verfügbar ist, kann das Backend für den
Prototyp in einen lokalen Demo-Modus fallen. Dieser Modus ist kein produktives
Persistenzverhalten und wird im Frontend sichtbar angezeigt.

== Mapping: Notifications

Im aktuellen Guide steht im Beispiel noch `notifications: []`. Da in Supabase bereits eine Tabelle `notifications` existiert, kann das Mapping dafür vorbereitet werden.

[cols="1,1,2", options="header"]
|===
| Datenbankfeld | API-Feld | Bemerkung

| `id`
| `id`
| Eindeutige ID der Notification.

| `subscription_id`
| `subscriptionId`
| Zuordnung zum betroffenen Abo.

| `type`
| `type`
| Art der Benachrichtigung, z. B. Kündigungsfrist oder Budgetwarnung.

| `trigger_date`
| `triggerDate`
| Datum, an dem die Benachrichtigung ausgelöst werden soll.

| `is_sent`
| `isSent`
| Gibt an, ob die Benachrichtigung bereits gesendet wurde.

| `message`
| `message`
| Nachrichtentext.
|===

Für das bestehende Frontend kann daraus zusätzlich eine vereinfachte Anzeige erzeugt werden:

[source,json]
----
{
  "id": 1,
  "icon": "⚠️",
  "color": "yellow",
  "msg": "Kündigungsfrist läuft bald ab",
  "meta": "in 5 Tagen",
  "unread": true
}
----

== Hinweise zum aktuellen Backend-Stand

Für die aktuelle Umsetzung in `backend/src/routes/dashboard.ts` und
`backend/src/routes/subscriptions.ts` gelten folgende Punkte:

* Der Endpoint sollte `GET /api/dashboard` heißen.
* Die Daten sollten im Backend aus Supabase/PostgreSQL gelesen werden.
* SQL-Felder werden im Backend auf camelCase gemappt.
* Für nutzerbezogene Daten muss nach `user_id` gefiltert werden.
* Datumswerte sollten im Format `YYYY-MM-DD` an das Frontend zurückgegeben werden.
* `numeric`-Werte aus PostgreSQL sollten als JavaScript-Number zurückgegeben werden.
* Fehlende optionale Werte sollten als `null` und nicht als `undefined` zurückgegeben werden.
* Das Frontend soll keine Service-Role-Keys oder Datenbank-Secrets enthalten.
