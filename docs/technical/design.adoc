== Wichtige Interaktionsflüsse

Die folgenden Sequenzdiagramme zeigen die systemübergreifenden Abläufe für die wichtigsten Anwendungsfälle (Use Cases).

=== Abo anlegen (PAP 1 / UC1)

_Dieser Fluss zeigt, wie ein neues Abonnement im System validiert und gespeichert wird, und wie sofort Erinnerungen eingeplant werden, falls eine Frist existiert [cite: 989-1008, 1435-1526]._

[plantuml, sequence-booking, svg]
....
@startuml
skinparam monochrome true
skinparam defaultFontSize 12

actor "Nutzer:in" as user
participant "Frontend\n(React)" as fe
participant "Backend\n(Express)" as be
participant "Datenbank\n(PostgreSQL)" as db

user -> fe : Formular ausfüllen & absenden
fe -> be : POST /api/subscriptions\n{name, cost, interval...}
be -> be : Serverseitige Validierung
alt Validierung fehlgeschlagen
    be --> fe : 400 Bad Request (Errors)
    fe --> user : Fehlermeldung anzeigen
else Validierung erfolgreich
    be -> db : INSERT INTO subscriptions...
    db --> be : savedSubscription
    opt Kündigungsfrist vorhanden
        be -> db : INSERT INTO notifications (Reminder)
    end
    be --> fe : 201 Created
    fe -> fe : Abo-Liste neu laden
    fe --> user : Erfolgsmeldung & neue Liste
end
@enduml
....

=== Tägliche Fristenprüfung (PAP 2)

_Ein asynchroner Hintergrund-Prozess, der völlig ohne Nutzerinteraktion abläuft. Er ermittelt fällige Kündigungen effizient über eine SQL-Abfrage [cite: 1018-1022, 1529-1582]._

[plantuml, sequence-deadline, svg]
....
@startuml
skinparam monochrome true
skinparam defaultFontSize 12

participant "Cron Job\n(node-cron)" as cron
participant "Datenbank\n(PostgreSQL)" as db
participant "Push Service\n(FCM/APNS)" as push

cron -> cron : Täglicher Timer (06:00)
cron -> db : SELECT fällige Abos (Frist < 7 Tage & nicht gesendet)
db --> cron : Liste fälliger Abos
loop für jedes Abo in Liste
    cron -> db : INSERT INTO notifications
    db --> cron : notification_id
    cron -> push : sendPush(userId, message)
    push --> cron : OK
    cron -> db : UPDATE notifications SET is_sent = true
end
@enduml
....

== Eingesetzte Muster & Konventionen

Um API-Vertragsbrüche (API Drift) zwischen Frontend und Backend zu vermeiden, wurde eine enge Kopplung der Datenstrukturen beschlossen [cite: 130-133, 1377-1380].

=== Designmuster

[cols="1,2,2", options="header"]
|===
| Muster | Wo eingesetzt | Begründung

| Shared TypeScript-Types
| `/shared/types.ts`
| Frontend und Backend teilen sich dieselben Interface-Definitionen. Ändert sich das Datenmodell, schlägt der Build sofort fehl [cite: 130-183, 1377-1430].

| Serverseitige Aggregation
| `/api/analysis` (PAP 3)
| Anstatt tausende Abos ans Frontend zu schicken und dort zu berechnen, summiert die Datenbank via `SUM()` und `CASE`-Statements die monatlichen Kosten extrem performant vor [cite: 340, 352-379, 1587, 1599-1626].

| Thick Backend (Fat Controller)
| `/api/import/csv` (PAP 4)
| Die rechenintensive Mustererkennung von Kontoauszügen liegt komplett im Node.js-Backend, damit der Browser-Tab des Nutzers nicht einfriert[cite: 468, 1715].
|===

=== API-Konventionen

[cols="1,3", options="header"]
|===
| Aspekt | Konvention

| URL-Struktur
| Ressourcenorientiert im Plural (z.B. `/api/subscriptions`, `/api/categories`).

| HTTP-Methoden
| Einhaltung der REST-Prinzipien: `GET` (Liste/Analyse), `POST` (Anlegen/Import), `PATCH` (Bearbeiten), `DELETE` (Löschen).

| Prepared Statements
| Bei *jedem* SQL-Query werden Variablen zwingend über `$1, $2` gebunden (z. B. `[req.user.id]`), um SQL-Injections vollständig auszuschließen [cite: 264-271, 696, 1511-1518, 1943].
|===
