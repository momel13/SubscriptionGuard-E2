Dieses Dokument beschreibt das technische Design von SubscriptionGuard: Code-Organisation,
Schichten, Komponenten, Datenmodell, zentrale Interaktionsflüsse, Designmuster und
Konventionen.
Es führt die systemweite Sicht aus `design (1).adoc` mit der detaillierten

== Systemübersicht und Schichtenarchitektur

SubscriptionGuard folgt einer 3-Schichten-Architektur plus externe Dienste. Dadurch bleiben
Benutzeroberfläche, Geschäftslogik und Datenhaltung getrennt.
Das Frontend kennt die
Datenbank nicht direkt, sondern spricht mit der Logikschicht über REST.

|Datenschicht
|Persistente Speicherung von Nutzern (inkl. Budget), Abos, Kategorien, Zahlungen und Notifications;

|Externe Dienste
|Standardisierte Dienste wie Authentifizierung und Push-Zustellung.
|Je nach Dienst.
|===

=== Backend-Komponenten

[cols="1,2,3",options="header"]
|===
|Komponente |Technologie |Verantwortung

|`subscriptions` Router
|Express + TypeScript
|Abo anlegen, listen, bearbeiten, löschen, pausieren/fortsetzen. Validiert Eingaben und
erzeugt Erinnerungen bei Fristen.

|`categories` Router
|Express + TypeScript
|Kategorien für Abo-Formulare und Auswertungen bereitstellen.

|`analysis` Router
|Express + SQL
|Monatskosten normalisieren, nach Kategorien gruppieren, Duplikate und Einsparpotenzial
berechnen.

|`budget` Router
|Express + SQL
|Monatsbudget aus `users` lesen/setzen und Status `NO_BUDGET`, `WITHIN_BUDGET`, `OVER_BUDGET` liefern.

|`import` Router
|Express + multer + csv-parse
|CSV-Dateien entgegennehmen, wiederkehrende Zahlungen erkennen und bestätigte Kandidaten als
Abos anlegen.

|`notifications` Router
|Express + SQL
|Erinnerungen und Warnungen für das Frontend bereitstellen.

|Deadline Job
|node-cron
|Täglich fällige Kündigungsfristen prüfen, Notifications erstellen und Push auslösen.

|Push Service Adapter
|FCM / APNS / Web Push
|Provider-spezifische Push-Zustellung kapseln.

|DB-Zugriff
|pg-Treiber / Supabase Client
|Prepared Statements, Connection Handling und Mapping von snake_case zu camelCase im einheitlichen PostgreSQL-Dialekt.
|===

=== Tabellenbeschreibung

[cols="1,1,3",options="header"]
|===
|Tabelle |Spalte |Beschreibung und Besonderheiten

.5+|`subscriptions`
|`id`
|Primärschlüssel.

|`interval`
|Enum-Constraint: `WEEKLY`, `MONTHLY`, `QUARTERLY`, `YEARLY`.
|`usage_rating`
|Nutzungsbewertung: `OFTEN`, `RARELY`, `NEVER`, `NOT_RATED`.
|`cancel_deadline`
|Datum, bis zu dem gekündigt werden muss;
Grundlage für PAP 2.
|`is_paused`
|Pausierte Abos werden bei Kostenanalyse und Fristenprüfung ignoriert.

.2+|`payments`
|`status`
|Zahlungsstatus: `PENDING`, `PAID`, `FAILED`.
|`subscription_id`
|Fremdschlüssel;
bei Löschung eines Abos werden Zahlungen kaskadierend gelöscht.

.3+|`notifications`
|`type`
|Warnungsart, z.B. `CANCEL_DEADLINE_REMINDER`, `PAYMENT_REMINDER`, `BUDGET_WARNING`.
|`trigger_date`
|Datum, an dem die Erinnerung ausgelöst wird.

|`is_sent`
|Verhindert mehrfaches Senden derselben Erinnerung.
|===

== REST-API-Konventionen

[cols="1,3",options="header"]
|===
|Aspekt |Konvention

|URL-Struktur
|Ressourcenorientiert im Plural: `/api/subscriptions`, `/api/categories`, `/api/notifications`.

|HTTP-Methoden
|`GET` für Listen/Analyse/Status, `POST` für Anlegen und Import, `PATCH` für Bearbeiten,
`DELETE` für Löschen, `PUT` für vollständiges Setzen wie Budget.

|Payloads
|JSON für Standardfälle, `FormData` für CSV-Upload.

|Namenskonvention
|API-Responses verwenden camelCase. Mapping von SQL snake_case passiert im Backend.

|Fehlerformat
|Validierungsfehler werden strukturiert zurückgegeben, z.B. `{ errors: string[] }`.

|SQL-Sicherheit
|Alle SQL-Variablen werden über Prepared Statements gebunden.
|===

[cols="1,1,2,3",options="header"]
|===
|Methode |Pfad |Use Case |Funktion

|POST |`/api/subscriptions` |UC1 / PAP 1 |Abo anlegen.
|GET |`/api/subscriptions` |F1 |Alle Abos auflisten.
|PATCH |`/api/subscriptions/:id` |F1 |Abo bearbeiten.
|DELETE |`/api/subscriptions/:id` |F1 |Abo löschen.
|POST |`/api/subscriptions/:id/pause` |F1 |Abo pausieren oder fortsetzen.
|GET |`/api/categories` |F1 |Kategorien laden.
|GET |`/api/analysis` |UC3 / PAP 3 |Kostenanalyse und Empfehlungen.
|POST |`/api/import/csv` |UC4 / PAP 4 |CSV hochladen und Vorschläge erhalten.
|POST |`/api/import/commit` |UC4 / PAP 4 |Vorschläge bestätigen und Abos anlegen.
|GET |`/api/budget/status` |UC5 / PAP 5 |Budgetstatus laden.
|PUT |`/api/budget` |UC5 / PAP 5 |Monatsbudget setzen.
|GET |`/api/notifications` |F4 / UC2 |Erinnerungen abrufen.
|===

== Wichtige Interaktionsflüsse

=== UC1/PAP 1: Abo anlegen

[plantuml,sequence-create-subscription,svg]
----
@startuml
actor "Nutzer:in" as User
participant "Frontend\nSubscriptionForm" as FE
participant "Backend\nSubscriptions Router" as BE
database "Datenbank" as DB

User -> FE : Formular ausfüllen und absenden
FE -> FE : Client-Plausibilität prüfen
FE -> BE : POST /api/subscriptions
BE -> BE : Serverseitige Validierung
alt Validierung fehlgeschlagen
  BE --> FE : 400 { errors }
  FE --> User : Fehlermeldungen anzeigen
else Validierung erfolgreich
  BE -> DB : INSERT INTO subscriptions
  DB --> BE : savedSubscription
  opt Kündigungsfrist vorhanden
    BE -> DB : INSERT INTO notifications
  end
  BE --> FE : 201 Subscription
  FE -> FE : Liste invalidieren / neu laden
  FE --> User : aktualisierte Abo-Liste
end
@enduml
----

=== UC2/PAP 2: Tägliche Fristenprüfung

[plantuml,sequence-deadline-check,svg]
----
@startuml
participant "Cron Job\nnode-cron" as Cron
database "Datenbank" as DB
participant "Push Adapter" as Push
participant "Backend\nNotifications Router" as BE
participant "Frontend\nNotification Center" as FE

Cron -> Cron : Täglicher Timer
Cron -> DB : SELECT fällige Abos
DB --> Cron : Liste fälliger Abos
loop für jedes Abo
  Cron -> DB : INSERT INTO notifications
  Cron -> Push : sendPush(userId, message)
  Push --> Cron : OK
  Cron -> DB : UPDATE notifications SET is_sent = true
end
FE -> BE : GET /api/notifications
BE -> DB : SELECT notifications
DB --> BE : Notification[]
BE --> FE : Notification[]
FE --> FE : Erinnerungen anzeigen
@enduml
----

=== UC5/PAP 5: Budget setzen und überwachen

[plantuml,sequence-budget,svg]
----
@startuml
actor "Nutzer:in" as User
participant "Frontend\nBudgetPage" as FE
participant "Backend\nBudget Router" as BE
database "Datenbank" as DB

User -> FE : Budget öffnen
FE -> BE : GET /api/budget/status
BE -> DB : Budget laden
alt Kein Budget
  BE --> FE : { status: "NO_BUDGET" }
  FE --> User : Budget setzen anbieten
else Budget vorhanden
  BE -> DB : Monatskosten berechnen
  alt Kosten > Budget
    BE --> FE : OVER_BUDGET
    FE --> User : roter Fortschritt + Warnung
  else innerhalb Budget
    BE --> FE : WITHIN_BUDGET
    FE --> User : grüner Fortschritt + Restbetrag
  end
end

User -> FE : Monatsbudget setzen
FE -> BE : PUT /api/budget
BE -> DB : UPDATE users SET monthly_budget
BE --> FE : gespeichertes Budget
FE -> BE : Status neu laden
@enduml
----

== Eingesetzte Muster und Konventionen

[cols="1,2,3",options="header"]
|===
|Muster |Wo eingesetzt |Begründung

|Shared TypeScript-Types
|`/shared/types.ts`
|Frontend und Backend teilen Interface-Definitionen. Änderungen am Datenmodell werden beim
Build sichtbar.

|Feature-orientierte Frontend-Module
|`frontend/src/features/*`
|Fachliche Bereiche wie Abos, Analyse, Budget und Import bleiben zusammenhängend wartbar.

|API Client Facade
|`frontend/src/shared/api/*`
|Komponenten rufen keine rohen `fetch`-Calls auf. Fehlerbehandlung und Typisierung bleiben
konsistent.

|Serverseitige Aggregation
|`GET /api/analysis`
|Kosten werden per SQL `SUM` und `CASE` normalisiert, statt alle Rohdaten im Frontend zu
berechnen.

|Backend für Import-Erkennung
|`POST /api/import/csv`
|CSV-Mustererkennung kann rechenintensiv sein und läuft stabiler im Backend.

|Scheduler
|`deadlineCheck`
|PAP 2 läuft ohne Nutzerinteraktion täglich automatisch.

|Adapter
|Push Service, Auth, DB-Zugriff
|Provider-spezifische Details bleiben gekapselt.

|Discriminated Union
|`BudgetStatus`
|Das Frontend muss alle Budgetzustände explizit behandeln.
|===

== UI-Zustände

[cols="1,3,3",options="header"]
|===
|Zustand |Wann |Darstellung

|Loading
|API-Daten werden geladen.
|Skeletons oder kompakte Ladeindikatoren pro Bereich.

|Empty
|Keine Abos, keine Analyse, keine Import-Kandidaten oder kein Budget.
|Kurzer Empty State mit passender Primäraktion.

|Validation Error
|Client- oder Backend-Validierung meldet Probleme.
|Fehler nahe am Feld; globale Fehlermeldung nur für formularweite Probleme.

|Permission Required
|Browser Notifications sind noch nicht erlaubt.
|Kontextbezogener Prompt im Notification-Bereich.

|Offline/API Error
|REST API nicht erreichbar oder Antwort fehlerhaft.
|Retry-Aktion und Daten nicht stillschweigend verwerfen.

|Over Budget
|Budgetstatus ist `OVER_BUDGET`.
|Roter Fortschrittsbalken, konkreter Betrag der Überschreitung.
|===
